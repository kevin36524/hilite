# 14.1 — Dynamic Project Discovery: HiLite changes (`HILITE.md`, progressive disclosure, routing tools)

**Status:** Spec / strategy — design locked 2026-06-07, not yet built
**Repo:** HiLite — `~/dev/ai/hilite`
**Parent:** [doc 14](14_dynamic_project_discovery.md) (the overall design & rationale).
**Sibling:** [doc 14.2](14.2_dynamic_project_discovery_app.md) (the YahooCoworker app
changes that consume the tools defined here).

This doc is the **HiLite-side** slice of doc 14: the new `HILITE.md` file format,
the progressive-disclosure loader that replaces the `HERMES.md`/`AGENTS.md`/
`CLAUDE.md` chain, and the new tools HiLite must register in `serve.py`. The app
side (sessions, picker, project-loader agent, deeplinks, callback routing) lives in
[doc 14.2](14.2_dynamic_project_discovery_app.md).

## 0. What HiLite must deliver

1. **Read `HILITE.md` only** as project context, treated as a *progressive-disclosure*
   doc (header always loaded; `## sections` on demand) — §2.
2. A **`hilite_section(name)`** tool that returns a section body on demand — §3.
3. Register four `ui_request` frontend tools so the app can implement the routing
   flow: `write_hilite_md`, `find_relevant_projects`, `open_project_session`,
   `report_to_parent` — §3. (HiLite only *exposes* these as tools and proxies them
   over the `ui_request`/`ui_result` channel; the behavior is implemented app-side,
   doc 14.2.)

## 1. Grounding facts (HiLite source, 2026-06-07)

1. **Today HiLite loads one flat project-context file by precedence**
   (`hilite/context.py`): `.hermes.md`/`HERMES.md` (walks to git root, **wins**) >
   `AGENTS.md` > `CLAUDE.md` (cwd only) > `.cursorrules`; only the top one, capped
   at 10 000 chars. **Decision (locked 2026-06-07): HiLite reads `HILITE.md` only.**
   The flat `HERMES.md`/`AGENTS.md`/`CLAUDE.md` chain is replaced by a single
   **`HILITE.md`** loaded as a *progressive-disclosure* doc (§2), which sidesteps
   the 10k cap because only the header loads by default. `HERMES.md` is no longer
   read. (HiLite is the user's own repo — this is a deliberate HiLite change.)
2. **Skills already implement progressive disclosure** — the exact pattern to copy.
   A skill is a markdown file with YAML frontmatter (`name`, `description`).
   `build_skills_index()` injects a tiny always-on index (`- name: description`
   lines); `load_skill(name)` returns the **full body on demand**
   (`hilite/skills.py:31,180,188`, `load_skill:157`). → `HILITE.md` mirrors this:
   header (frontmatter + overview) always loaded; `## sections` loaded on demand.
3. **cwd is immutable per process, but the shell reaches anywhere** (doc 13 §1.2):
   a session can `git -C <path>`, `ls <path>`, read/write files at any path without
   rooting there. → a session can derive context for, and write the `HILITE.md` of,
   a repo it isn't rooted in (used for first-time registration, driven app-side).
4. **The `ui_request`/`ui_result` blocking channel is generic** (doc 11.2/13):
   `write_hilite_md` / `find_relevant_projects` / `open_project_session` /
   `report_to_parent` are just frontend tools proxied over it.
5. **A `hilite --serve` (or one-shot) is cheap to spawn** (doc 12/13 run many side
   by side) — relevant because the app spins up a short-lived loader agent (doc 14.2 §6).

**Consequence:** the HiLite work is one new file type (`HILITE.md`, modeled on
skills) + one load-on-demand tool + four pass-through `ui_request` registrations.

## 2. `HILITE.md` — the progressive-disclosure project file

One per repo, at the repo root. **Tool-managed and dedicated** (not a human doc
like `CLAUDE.md`), so the app owns it fully — no sentinel-block dance, and we never
touch the repo's `CLAUDE.md`.

```markdown
---
name: mail-api
description: Mail backend (Python/FastAPI). REST under /v1/*. Build `make build`, test `pytest`.
project: Yahoo Mail
role: BE
siblings:
  - mail-web (FE) — ../mail-web
---

## Overview
mail-api serves the Mail backend. Always-loaded, kept to a few lines — the
fast path for a session rooted here and the routing signal for the loader agent.

## Build & test            <!-- detail section: loaded on demand -->
…

## Public surface / contracts
…

## Conventions
…
```

- **Always loaded** when a session roots in this repo: the frontmatter +
  `## Overview` only (a few hundred tokens) — context stays small.
- **On demand:** any `## Section` is fetched by name via `hilite_section` (§3),
  exactly like `load_skill`. So even a big repo's `HILITE.md` never bloats the prompt.
- **The frontmatter `name` + `description`** are what the **global project index**
  is built from (app-side, doc 14.2 §2.1) — the only thing the loader agent reads
  across all repos. HiLite's job is just to make the header cheaply parseable (reuse
  the skills frontmatter parser).

### 2.1 Loader behavior

When a session starts with `cwd = <repo>`:
1. Look for `HILITE.md` at the repo root.
2. If present, load **only the header** (frontmatter + `## Overview`) as project
   context, and emit a TOC of the other `##` section names so the agent knows what
   it can pull with `hilite_section`.
3. If absent, load no project context — the app drives first-use registration
   (doc 14.2 §5) which ends in a `write_hilite_md` call.

The 10k char cap that applied to the flat file is effectively moot because only the
header loads by default; individual sections fetched via `hilite_section` can carry
their own (looser) bound if needed.

## 3. New / changed tools (HiLite side)

| Tool | Kind | Notes |
|---|---|---|
| `hilite_section(name)` | load-on-demand (like `load_skill`) | returns a `## section` body from the current repo's `HILITE.md` |
| `write_hilite_md(path, frontmatter, overview, sections)` | `ui_request` | proxied to the app, which writes/refreshes the file + index (doc 14.2 §5) |
| `find_relevant_projects(request)` | blocking `ui_request` | proxied to the app, which runs the side loader agent over the global index and resolves with matches (doc 14.2 §6.1) |
| `open_project_session(project, repo, task, context)` | `ui_request`, resolves immediately | proxied to the app, which spawns the child `.scoped` session + posts the deeplink (doc 14.2 §6.2) |
| `report_to_parent(summary)` | `ui_request`, resolves immediately | proxied to the app, which delivers the child→parent callback (doc 14.2 §6.3); no-op if the session has no parent |

**HiLite changes, concretely:**
- **Read `HILITE.md` only** as project context (drop the `HERMES.md`/`AGENTS.md`/
  `CLAUDE.md` chain — §1.1) and treat it as a **progressive-disclosure** doc:
  always-load the header (frontmatter + `## Overview`); list other `##` sections in
  the header's TOC; add a **`hilite_section`** tool to fetch a section on demand
  (reuse the skills frontmatter parser + `load_skill`-style body slicing,
  `hilite/skills.py`). Likely a small `hilite/context.py` change (or a new
  `hilite/hilite_doc.py`).
- **Register the four `ui_request` tools** in `serve.py` (same plumbing as doc 13
  §4.1 / doc 11.2 — the `ui_request`/`ui_result` blocking channel already exists).
  HiLite does not implement their behavior; it only declares the tools and forwards
  the calls to the frontend, which resolves them (doc 14.2).

## 4. Files: new vs changed (HiLite — `~/dev/ai/hilite`)

**New / changed**
- `hilite/context.py` (or a new `hilite/hilite_doc.py`) — read **`HILITE.md` only**
  as a progressive-disclosure doc: parse frontmatter (reuse `hilite/skills.py`),
  load header always, expose section names, slice a `## section` body on demand.
  Drop the `HERMES.md`/`AGENTS.md`/`CLAUDE.md`/`.cursorrules` precedence chain.
- `hilite/skills.py` — reuse `load_skill`-style body slicing for `hilite_section`
  (factor out the shared section-slicing helper if convenient).
- `serve.py` — register `hilite_section` (load-on-demand) and the four `ui_request`
  tools (`write_hilite_md` / `find_relevant_projects` / `open_project_session` /
  `report_to_parent`) on the same `ui_request`/`ui_result` plumbing as doc 13 §4.1.
- `tests/` — unit-test the `HILITE.md` parser + section slicing (header-always /
  sections-on-demand); a test that `HERMES.md` is no longer read.

## 5. Acceptance criteria (HiLite side)

1. **`HILITE.md`-only context.** A session rooted in a repo with a `HILITE.md` loads
   that file's **header** as project context and reads **no** `HERMES.md`/`AGENTS.md`/
   `CLAUDE.md`.
2. **Progressive disclosure.** A `## Build & test` section is absent from the initial
   context and is returned only when the agent calls `hilite_section("Build & test")`.
3. **TOC exposure.** The header context lists the other `##` section names so the
   agent knows what it can fetch.
4. **Tools registered.** `hilite_section` resolves locally; `write_hilite_md`,
   `find_relevant_projects`, `open_project_session`, and `report_to_parent` are
   declared and correctly proxied over `ui_request`/`ui_result` (the app resolves
   them — verified end-to-end in doc 14.2).
5. **No `HILITE.md` ⇒ no project context** loaded (first-use registration is driven
   app-side and ends in `write_hilite_md`).

## 6. Build order (HiLite side)

1. **`HILITE.md` format + loader + `hilite_section`** — header-always /
   sections-on-demand, modeled on skills. Unit-test the parser + section slicing.
   (Maps to doc 14 build-order step 1.)
2. **Register the four `ui_request` tools** in `serve.py` so the app can implement
   `write_hilite_md` (step 2), `find_relevant_projects` (step 4),
   `open_project_session` (step 5), `report_to_parent` (step 6). HiLite only needs
   the declarations + proxying in place; behavior is verified from the app side.

## 7. Open questions (HiLite-relevant)

- **Section fetch bound.** Should `hilite_section` cap a returned section's size, or
  trust authoring discipline? (The header is always small; sections are the risk.)
- **Frontmatter parser sharing.** Factor the skills frontmatter/section-slicing into
  a shared helper, or copy it for `HILITE.md`?
- See [doc 14 §12](14_dynamic_project_discovery.md) for the cross-cutting open
  questions (orchestrator retirement, loader confidence, multi-hop depth, index
  location — most are app-side).

**Resolved (2026-06-07):** HiLite reads **`HILITE.md` only** (not `HERMES.md`), as a
progressive-disclosure doc (§1, §2).
